# 工程原则：单一事实源、解耦、原子化、先复用

> 所有实现与重构的总则。与局部写法冲突时，先满足本文件，再谈局部风格。
> 分层与目录细节见 `../conventions/layered-architecture.md`、`../conventions/module-layout.md`；组件复用见 `../conventions/ui-system.md`。

## 1. 单一事实源

- 一个概念只能有一个**手写作者源**；其余值必须由它派生。
- 出现第二份手写实现，视为已经在漂移：先合并，再继续做功能。
- 典型必须共享的派生逻辑：
  - 计数/汇总：领域层某模块的计数函数；调用方不要再写一遍循环累加
  - 筛选：领域层的筛选函数，不要在页面里复制条件
  - 排序：领域层的排序函数，读与写共用同一实现
  - 标识：统一的新标识生成函数
  - 标签映射：枚举值到显示文案的映射函数
  - 成对字段转换：领域层的转换函数，不要在适配层各写一份
  - 数据加载：共享数据加载模块的统一入口，不直接请求静态文件
  - 序列化：写入层的格式化函数，读与写共用
  - 名称归一/匹配：先查现有工具模块；没有就抽，不允许第三份
- **值可以重复，规则不能重复**：同一常量（超时、断点、颜色）只在一处定义；样式 token 与脚本配置各保留一份时，必须写明谁是源、谁从谁读。
- 样式值只从 token 取：不在脚本或行内样式里二次硬编码主题值。

## 2. 解耦：一层只认识下一层

- 依赖方向固定，自下而上：通用层 → 领域层 → 适配层 → 页面层；服务层独立于前端。
  - 通用层：不引用页面、不引用业务模块
  - 领域层：纯计算，不引用页面层与适配层，不使用运行时全局对象、DOM、网络请求、本地存储
  - 适配层：把领域数据翻译成具体运行时对象（视图节点、请求、存储），领域层不反向依赖它
  - 页面层：可引用下层；页面之间不互相引用
  - 服务层：独立于前端，不读前端模块
- **领域模型只做纯计算**：成对字段用普通数据（对象或数组）表达；运行时对象、DOM 节点、网络请求放在适配层或页面层。
- **适配层负责翻译**：渲染适配、数据传输适配、存储适配都只做格式转换，不承载业务判断。
- **不为「以后可能用」留口子**：没有调用点的参数、导出、开关、默认分支删掉。删参数比加注释警告更可靠。

## 3. 原子化：一个文件/函数只做一件事

- 一个文件一个关注点。文件名要能回答「它负责什么」，而不是「它里面有什么」。
- 新文件目标 ≤ 300 行；函数 ≤ 60 行；圈复杂度 ≤ 10；嵌套 ≤ 3。
- 超限时**抽函数**，不是压行、拆表达式、加注释。
- 文件组织顺序：模块入口 → 公开函数 → 私有工具；不要先铺一堆 helper。
- 状态只放在需要它的最小作用域：能用参数传的，不做模块级可变状态；确需模块级状态（如共享缓存、渲染上下文）必须只有一个设置入口。

拆分判断：

| 症状 | 处理 |
|---|---|
| 函数名里出现「和/并/以及」 | 拆成两个函数 |
| 读一个函数要先记 4 个以上局部状态 | 抽状态对象或拆阶段 |
| 改 A 功能必须理解 B 功能的代码 | 拆文件/拆模块 |
| 同一段结构/样式第二次出现 | 抽组件或模板 |
| 同一段数据变形第二次出现 | 抽共享函数 |
| 只有一个调用点且没有复用价值 | 不抽，保留内联 |

## 4. 先复用，再造轮子

- 动手前先搜：同名函数、同类组件、相似结构、相似样式规则。
- 已有组件能覆盖 80% 就扩展它，不要复制一份「稍微不一样」的。
- 新增抽象的门槛：**第二次真实使用**，或第一次就有明确的跨页面契约。不要为单个调用点设计框架。
- 禁止绕开统一组件另起一套：
  - 原生下拉控件 → 用统一下拉组件
  - 原生日期输入 → 用统一日期控件
  - 自建遮罩/浮层 → 用统一浮层组件
  - 自建抽屉/面板 → 用统一面板组件
  - 自建级联选择 → 用统一级联组件
  - 直接请求静态数据 → 用统一数据加载入口
- 统一组件不足时，先改组件、迁移所有调用点，再提交；不要「新代码用新组件，旧代码保留旧实现」。

## 5. 边界与契约

- 每个模块的公开面尽量小：只导出调用方真正需要的函数/常量。
- 函数参数要窄：只传它用到的数据，不传「万能上下文」。
- 返回结构要稳定：成对字段统一同一结构，日期统一 `YYYY-MM` / `YYYY-MM-DD`，标识统一字符串。
- 同一类量固定单位与取值域（如长度用基本单位数值、比例用 `0..1` 小数），并写在文档里；不要在调用点临时换算。
- 空值语义显式化：
  - 空字符串不等于 `0`，也不等于「没有」
  - 成对字段要么都有、要么都没有
  - 可选字段用 `null`/缺失表达，不用魔法默认值
- 错误不要静默吞掉：只吞可恢复的异常类型（如极端输入下本就无定义的分支），其余让它暴露；降级必须写日志或状态。
- 校验与保存共用同一实现：不能只在界面层拦截，写入路径必须再校验一次。

## 6. 重构纪律

- **一次只改一件事**：结构搬移与行为修改分开提交。
- 抽函数 = 纯搬运：签名、语义、副作用逐字对照；搬完原有验证必须通过。
- 删除要彻底：死代码、死样式、旧 id/class、旧 export 同批删除，并用全仓搜索证明无引用。
- 不做「顺手大扫除」：与当前任务无关的缺陷先登记，不打断当前项；除非它阻塞本次验收。
- 重构后目录、文档同步更新，README 里的路径、入口名、数据结构不能停留在旧版本。

## 7. 规模预算与逐步收敛

- 新文件目标 ≤ 300 行，新增函数目标 ≤ 60 行；这是提醒拆分的预算，不是为了凑数字而拆。
- 已有超限文件不强制一次拆完；下次改到它时，优先把本次触碰到的独立职责拆出去，避免继续膨胀。
- 拆分不能改变行为；拆文件/抽函数与改功能分开做、分开验证。
- 单次改动新增的重复实现为零：评审时先搜「是否已有同名/同义函数」。

## 8. 评审快查

1. 这个逻辑是否已有共享实现？在哪？
2. 依赖方向对吗？领域层是否碰了运行时对象、网络或存储？
3. 文件/函数是否只做一件事？是否超过预算？
4. 是否出现第二套下拉/浮层/面板/加载/格式化？
5. 单位、取值范围、空值、失败、边界是否显式处理？
6. 删除是否彻底？是否留下旧 class/id/export？
7. 文档是否同步？验证是否覆盖真实页面、接口与刷新后的状态？

提交流程另见 `../checklists/change.md`。
