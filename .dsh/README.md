# `.dsh/` 索引

> 根 `AGENTS.md` 是唯一自动加载入口；本目录按需读取，不要求一次读完。
> 只放「跨项目成立的纪律」和「按技术面取用的约定」，不放任何具体项目的业务事实。

## 术语

| 词 | 含义 |
|---|---|
| 派生值 | 由主数据算出、不手写的值：统计、标签、排序结果、格式化输出 |
| 成对字段 | 同一实体上必须同时存在或同时为空的字段：起止、上下界、两个端点、原文/译文 |
| 静默失败 | 程序不报错、流程照走，但结果已经错了 |
| 完成四层 | 代码存在 → 被调用 → 被消费 → 持久化/可见 |
| 统一组件 | 同一交互在项目里只能有一份实现，新增入口必须复用它 |

## 规则怎么用

1. **核心四条无条件生效**，与任务类型无关；`conventions/` 按技术面取用，没有对应技术面就不读。
2. 项目专属事实（目录树、端口、字段、命令、术语）写在**项目自己的** `AGENTS.md` 与项目 `.dsh/conventions/`，不进本库；冲突时项目事实优先。
3. 规则之间按主题互引，不复制同一段话；两处说法冲突，取更严格的一条并改掉另一处。
4. 只写「现在是什么」「为什么」「怎么算通过」；不写日期、作者、版本、变更叙事。
5. 新增条目的门槛：同类问题至少出现两次，或一次事故代价足够高。一次性偏好写进任务，不进规则。
6. 每条纪律尽量带可执行判据：能落成命令/检查的写成命令；不能机检的写清评审判据。

## 从外部项目引入时的判据

外部做法只作为启发，不默认适用。引入前逐条问：

1. **它解决的是真实出现过的问题吗？** 没有对应问题不引入。
2. **它依赖的前提我们有吗？** 没有就降级为人工检查或放弃。
3. **成本小于风险吗？** 为了「看起来规范」新增的门、目录、文档、状态机一律拒绝。
4. **术语能映射到目标项目吗？** 映射不了说明属于别的领域，不要照搬名词。
5. **能被验证吗？** 不能验证的只能写成建议，不能写成硬约束。

保留原则，丢掉仪式：保留「完成要验证」，不要求接入外部流程体系；保留「单一事实源」，不照搬外部编号。
