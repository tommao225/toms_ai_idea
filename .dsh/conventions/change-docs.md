# 变更文档：方案、排查、决策

> 这份约定只回答三件事：什么时候要写、写哪一种、写成什么样才算能用。
> 文档放在哪个目录、文件怎么命名，由各项目自己的文档索引决定。

## 1. 项目事实和改动过程分开

| 写什么 | 放哪里 |
|---|---|
| 项目现在的事实：用法、字段、规范、当前结构 | 项目自己的文档 |
| 一次改动怎么发生、为什么这么选 | 项目约定的变更文档目录 |
| 多个项目都适用的规矩 | 规则库 |

判断方法：如果代码明天重构，这份文档会过时吗？会，放项目文档；不会，放变更文档。

同一件事只写一处。变更文档写“为什么变、怎么变”，不抄项目文档里的字段表和结构；做完之后，把“现在是什么”写回项目文档。

## 2. 什么时候必须先写方案

| 情况 | 要不要先写 |
|---|---|
| 改数据格式、公开网址或编号、跨层改动（比如页面直接读写数据）、超过 3 个文件、超过 1 人日、不可逆（改了很难退回）、方案有真实分歧 | 必须写 |
| 2–3 个文件、半天内能做完、原因清楚 | 可以不写，在提交说明里写清改了什么 |
| 单文件、半小时内、不影响数据和接口 | 不写 |

同一件事不要写三份文档：

- 问题清单是方案里的一节，不单独写“问题文档”。
- 方案和做法写在同一份里。
- 长期有效的选择另写一份决策记录，方案里只写结论并指过去。
- 只有原因复杂、跨项目、查了很久的故障，才单独写排查记录。
- 只有发现很多、或者要评审别的项目时，才单独写评审记录。

## 3. 写哪一种

下面用 P0 表示挡住开工，P1 表示这一批必须修，P2 表示可以晚点。

| 类型 | 回答什么问题 | 什么时候写 |
|---|---|---|
| 方案 | 要做什么、怎么实施、怎么算做完 | 达到第 2 节的条件 |
| 排查记录 | 为什么坏了、怎么修、怎么防再次发生 | 原因不清楚，或查了超过 1 小时 |
| 决策记录 | 为什么选这个、不选那个 | 不可逆、有争议、以后会被反复问 |
| 评审记录 | 现在有什么问题、证据是什么 | 可选，发现多或跨项目时 |

不单独写的：调研并进方案；事故复盘并进排查记录；变更日志看 git；需求和待办用方案状态表达；会议记录、日报、周报不写；使用说明、接口文档、产品说明放项目文档；规则放规则库。

## 4. 方案写什么

1. **背景与目标**：为什么现在做，做完能看到什么变化，明确不做什么。
2. **现在的情况**：只写事实和证据，文件、命令输出、截图；没验证的标“待验证”。
3. **问题清单**：编号、级别、问题、影响、依据。
4. **怎么做**：至少两个方案，包括“不做”；写清选哪个、为什么，别的为什么不选。
5. **分几步做**：每一阶段做什么、做完什么样、前后依赖、出问题怎么退回。
6. **怎么算做完**：每一项写清怎么查、通过标准是什么，不写“功能正常”这种话。
7. **风险和要先定的事**：可能出什么问题、怎么应对；开工前必须先定的选择，写清谁在什么时候定。
8. **任务清单**：每个任务写清做什么、大概几天；第一件事不超过 1 天。

写法要求：

- 问题表只写问题和影响，具体方案放第 4 节，不在表里展开。
- 至少两个方案，包括“不做”。只有一个方案，说明还没想清楚，或者这件事不该做。
- 第 2 节只写事实，不在这里重复第 3 节的问题表。
- 第 5 节写阶段目标，第 8 节写具体任务，两边不重复同一段话。
- 第一阶段不超过 1 天；拆不出来，说明范围太大。
- 单文件不超过 300 行；超了先删重复，再考虑拆。

## 5. 什么时候算能开工、算做完

能开工：

1. 每个 P0、P1 都有结论，没有“待定”。
2. 第一件事不超过 1 天，而且不被没定的事挡住。
3. 每一项检查都能执行，或者能明确看到结果。
4. 不可逆的步骤有退回办法或迁移办法。

算做完：

1. 每一项检查都有结果，失败项写清原因。
2. 项目文档已经改成现在的事实。
3. 该写的决策记录已经写。
4. 索引和状态已经更新。

不满足就保持“草稿”或“进行中”，不要用“基本完成”代替。

## 6. 命名、状态、索引

- 文件名由类型前缀、日期或序号和中文短名组成，段与段之间用短横线；短名用中文，不用英文或拼音。README 是索引文件，保留英文名。
- 日期用创建当天，写在文档开头，不写进正文。
- 状态用固定几个词：草稿、已确认、进行中、完成、被替代、不修。具体字段名由项目的文档索引约定。
- 状态只写在文档开头。索引里可以显示状态，但以文档为准。
- 新文档和索引要在同一次提交里更新；没登记的文档算漏写。
- 不建 `archive/` 目录；用“完成”或“被替代”表示结束。移动文件会让原来的链接失效。
- 决策记录确认后不改正文；要改就新写一份，旧的标“被替代”，并注明被哪一份替代。

## 7. 写给人看

文档是写给人看的，不只是给写代码的人看。

- 读者是项目所有者：懂需求和取舍，不一定读过实现。
- 专业词第一次出现时，用一句话解释；能用日常中文说清，就不用术语。
- 不写口号、排比和空泛总结。删掉“值得注意的是”“综上”“本质上”“不难发现”“众所周知”这类话。
- 不连续使用“不是……而是……”。一句话能说完，不拆成三段。
- 一段只讲一件事，先结论后理由。
- 同一件事只写一处。问题清单里不写方案，方案里不重复问题，做完不把当前事实再抄一遍。
- 表格只用来比较多项；叙述用段落。
- 少用加粗和破折号，让标题和句子自己表达结构。
- 有证据再下结论：文件、命令输出、截图；没验证的写“待验证”。
- 单文件不超过 300 行；超了先删重复，再考虑拆。

## 8. 评审快查

1. 这份文档回答的是“为什么变”，还是又把项目现在的事实写了一遍？
2. 每个问题都有级别、影响和依据吗？P0、P1 都有结论吗？
3. 有没有至少两个方案，包括“不做”？
4. 第一件事是否不超过 1 天？每项检查是否都能执行？
5. 不可逆的步骤有没有退回办法？没定的事有没有写谁在什么时候定？
6. 做完后，项目文档有没有更新成现在的事实？索引和状态有没有同步？
7. 文档里的术语，第一次出现时解释了吗？有没有空话、重复和明显的套话？
