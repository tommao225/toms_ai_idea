# 运行时骨架：固定步长、命令通道与确定性

## 背景

- 要解决的问题：世界怎么被改、时间怎么走，决定撤销、回放、存档、测试能不能做。
- 约束：格子模拟要可复现；后期想加撤销、回放、录像与自动测试；单人加 AI 写代码，必须能靠测试兜底。
- 不决策的代价：先写「界面直接改数组」，以后每加一个功能都要补一套只有它能用的改法。

## 决策

1. 固定步长，每秒 20 tick，渲染只插值，不推进世界。
2. 外部改动只走命令：界面与渲染拿只读视图，生成命令，由 `app/` 派发。
3. 确定性：随机只来自世界持有的种子源；遍历顺序固定；模拟里不读系统时间。
4. 每步一条命令前存快照，撤销与回放都基于快照加命令序列。
5. 模拟入口包一层 `SimClock` 接口，v1 同步实现，以后换 Worker 只换实现。

## 备选

| 方案 | 做法 | 为什么不选 |
|---|---|---|
| 界面直接改状态 | 点击后直接写网格 | 撤销只能整档快照，回放做不出来 |
| 可变步长 | 用真实帧间隔推进 | 结果依赖机器性能，回放不一致 |
| 每帧存全量快照 | 每帧复制整个世界 | 内存吃光，没有必要 |
| 纯函数式整体替换 | 每次返回全新世界对象 | 大网格复制开销高，调试也不直观 |
| v1 就上 Worker | 一开始把模拟放线程 | 调试变难，收益在 v1 不明显 |

## 后果

- 每个界面操作都要定义命令类型，前期有模板代码。
- 撤销、回放、录像、自动测试共用一条通道，后期加这些功能不用改世界。
- 快照有内存预算，撤销栈要限制份数。
- 以后换引擎或换线程，只替换 `SimClock` 的实现。
