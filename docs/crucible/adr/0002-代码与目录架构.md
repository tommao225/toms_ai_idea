# 代码与目录架构

## 背景

- 要解决的问题：W0 就要建目录。目录和分层一旦定错，后面每次改功能都要跨目录搬文件。
- 约束：单人开发；AI 会大量参与写代码；没有历史代码可参考。
- 不决策的代价：文件长成大杂烩，改一个功能要翻五个目录，AI 和人都会在同一处犯错。

## 决策

1. 顶层按「东西」分：`docs/`、`data/`、`src/`、`assets/`、`tests/`、`web/`，不按语言或文件类型分。
2. `src/` 按玩家能说出口的概念分：`world/`、`devices/`、`render/`、`ui/`，外加 `app/` 装配层与 `events.ts`。（原表里的 `crew/`、`contracts/` 已按 ADR-0004 删除。）
3. 依赖单向。渲染与界面只读状态，输入只产生命令，命令由 `app/` 派发。
4. 不设 `utils`、`helpers`、`common`、`shared` 这类空桶。
5. 目录层级不超过 3 层，文件不超过 300 行，同一目录不超过 15 个文件。

## 备选

| 方案 | 做法 | 为什么不选 |
|---|---|---|
| 按技术层分 | `models/`、`services/`、`controllers/` | 框架词，人找东西要猜；这个项目没有这些角色 |
| 按文件类型分 | `js/`、`css/`、`json/` | 与领域无关，改一个功能仍要到处跳 |
| 每个装置一个子目录 | `devices/pump/`、`devices/valve/` | 八种装置目录比文件多，反而更难找 |
| 全部平铺 | 不分子目录 | 文件一多就找不到 |
| 设一个 `shared/` 桶 | 所有跨层东西塞一起 | 桶会变成第二个 `utils` |

## 后果

- W0 按 `crucible/docs/03-architecture.md` 建目录，首次提交只有骨架与占位说明。
- 加物质只改 `data/`；加装置改一个实现文件加注册一行。
- 依赖方向要有一个检查脚本，W0 建目录时一起建。
- 以后要改结构，新写 ADR，旧文档标 `superseded`。
