# 技术与渲染架构

## 背景

- 要解决的问题：引擎、渲染方式与美术呈现方式都没定，导致渲染架构、资产预算和打包管线都无法开工。
- 约束：单人开发；第一目标是 itch 网页 demo，Steam 以后再说；画面九成面积是流体与材质；要有会走动的角色；素材预算有限，不可能整包外包。
- 不决策的代价：W0 无法启动；美术和代码各自猜一套架构，后期必然返工。

## 决策

1. 引擎用纯 Web：Vite 加 TypeScript 加 PixiJS。模拟内核写成不依赖 DOM 的纯 TS 模块，浏览器与以后的 Electron 壳共用；上 Steam 时只换外壳。
2. 呈现用混合方案：材质与流体用 32×32 可平铺贴图加程序化光照；角色、装置、界面用手绘。
3. 渲染只画摄像机可见的格子，一格 32 px，1080p 下约 2000 格。模拟与渲染解耦，模拟可放 Web Worker。
4. 角色是二到四名操作员，48×64 px，四方向，每名约 40 帧，状态机只有待机、走、搬、操作四态，不做寻路与需求。
5. 物质与装置做成数据表，MVP 只开放少量，上限是十种物质、八种装置。

## 备选

| 方案 | 做法 | 为什么不选 |
|---|---|---|
| 纯色块 | 只用纯色与假环境光遮蔽 | 不满足「要比线条更像实物」的要求 |
| Godot 4 | 用原生引擎做 | 放弃网页 demo；GDScript 跑格子模拟偏慢；要重学引擎 |
| Electron 优先 | 先做桌面再补网页 | 与「先上 itch」的目标冲突，网页 demo 会变成二等品 |
| 全手绘 | 包括流体也交给画师 | 流体是连续变化的，手绘追不上；六到十周、数万元，玩法一变就返工 |
| 整图 ImageData 渲染 | 每帧重画整张图 | 材质只能做到一格一像素，混合方案的优势用不上 |
| 带需求与寻路的小人 | 做完整的居民模拟 | 单人项目扛不住，会拖死主线 |

## 后果

- 需要同步改动的地方：`crucible/docs/02-art.md` 的资产清单与分级、`crucible/docs/01-design.md` 第 10 节的操作员规格、方案的 W0 任务。
- 新增的约束：光源统一左上，所有手绘资产同向；物质与装置只增数据不改代码；渲染只画可见格；操作员不做寻路与需求。
