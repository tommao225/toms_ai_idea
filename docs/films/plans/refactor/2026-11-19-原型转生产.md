# 原型转生产：数据结构、列表密度与管线

## 1. 背景与目标

原型已经有目录、放映单、详情、观影册四个页面，在 1440 和 390 宽度下能看出想要的感觉。但页面只放了 1 部示例片，没有真实数据；中间宽度和 100 行的真实列表也没试过。现在开始正式开发，先把数据结构和视觉标准定下来，再按一条完整的小流程逐步实现，避免把原型里的临时做法写进正式代码。

目标：

- 正式页面不再写死示例数据，页面上每个字段都能在 `data/` 里找到来源。
- 100 部片的放映单在 1440、1024、700、390 四个宽度都能用，键盘也能操作。
- 先拿 20 部真片跑通“抓取 → 合并 → 取色 → 生成 → 页面读取”，连续生成两次结果一致。数据管线指的是把电影数据抓下来、合并、生成页面用文件的一套脚本。
- 在 W3 检查通过前，`prototype.html` 一直保留，用来对照。

不做：

- 不做奖项、其他榜单口径、洲榜。
- 不做离线应用、服务端、登录。
- 首期不用真实剧照和第三方台词；是否保留占位，第 7 节再定。

## 2. 现在的情况

已经试过的：

- 四个页面在 1440 和 390 宽度下能打开；长片名、短片名、有无奖项、打卡状态都有截图。
- 行式排布、编号、卷标、盖章这些视觉规则，已经落在原型的 CSS 里。

还没试过或不够的：

- 100 部片的真实列表、每 10 部一卷、卷标吸顶、分批渲染。
- 560–820 宽度没有专门检查。
- 中文字体没有随站点一起提供，换一台机器字形会变。
- 真实数据、自动化检查都还没有。

数据、页面和工程上的具体问题见第 3 节。

## 4. 怎么做

| 方案 | 做法 | 代价 | 风险 |
|---|---|---|---|
| A 直接改原型 | 拆开 `prototype.js`，再补数据读取 | 最快 | 宽度切换、节点数和规范冲突都会带进正式代码 |
| B 从零重写 | 不看原型代码，只照截图 | 干净 | 长片名、描边字、盖章这些已经试好的细节要重做 |
| C 原型留作对照 | 保留 `prototype.html`；正式页面按数据结构和真实密度重新搭，能复用的 CSS 继续用 | 中等 | 两套页面会同时存在一段时间，要明确哪套算准 |

选 C。原型已经试出了长片名、描边字、盖章这些细节，直接扔掉可惜；但它的页面结构、宽度处理和列宽测量方式不适合继续加功能。所以原型只作为视觉对照，正式页面重新搭。这样 W1 的测试数据和 W2 的管线还能同时做。

会改变做法的几个选择放在第 7 节，定完再开工。

## 5. 分几步做

| 阶段 | 目标 | 做完什么样 |
|---|---|---|
| W0 定约定 | 定数据结构，定几个关键选择，装好环境 | 页面每个字段都有来源；5 份决策记录有结论 |
| W1 撑满列表 | 用 100 条测试数据把列表撑满，修宽度和字体 | 四个宽度不溢出；节点数达标；键盘能走完 |
| W2 跑通管线 | 先拿 20 部真片跑通抓取、合并、取色、生成 | 连续生成两次结果一致；缺字段就标缺，不猜 |
| W3 搭正式页面 | 正式页面骨架和打卡 | 四个页面可用；盖章不跳顶；空白和错误页面有处理 |
| W4 补第一榜 | 悬疑榜补到 60–100 部，每部写一句手记 | 数据检查全过；抽查没有凑数感 |

先后关系：

- W1 可以和选片同时做，不用等内容。
- W2 要先有数据结构和 Python、Pillow（图片处理库），以及 TMDb（电影数据源）的访问密钥。
- W3 要先有 W2 生成的 20 部电影数据。
- W4 要先有 W2 的电影主档；W3 可以先用 W1 的测试数据检查。

怎么退回：

- 原型文件不删、不改名，W3 检查通过前一直能打开。
- 新页面和原型同时存在，页面地址不冲突；数据只增不删；榜单编号和电影编号不改。
- 字体和 CSS 按文件改，不动 `tokens.css` 里已有的值。

## 6. 怎么算做完

| 检查面 | 怎么查 | 通过标准 |
|---|---|---|
| 字段 | 人工对照 01 和页面 | 页面上的每个字段都能在数据结构里找到，没有写死的示例 |
| 数据 | `python -m pytest films/tests`（W0 建） | 榜单条数等于条目数；名次从 1 连续；电影存在；奖项名存在 |
| 生成 | `python pipeline/build.py && git diff --exit-code` | 连续两次生成没有差异；失败时退出码不是 0 |
| 四个宽度 | 1440、1024、700、390 截图 | 页面不横向溢出；没有重叠和裁切 |
| 100 行列表 | 页面节点计数 | 不超过 1200，或按决策记录里的新上限 |
| 键盘和盖章 | Tab 走完 100 行；在第 50 行盖章 | 焦点看得见；长片名能看到全名；盖章后页面不跳 |
| 字体 | 断网并禁用系统字体后截图 | 和对照版本一致；列宽不漂移 |
| 第一屏 | 第一屏要加载的 HTML、CSS 和数据大小 | 不超过 150KB（不含海报和字体，字体上限按决策记录） |
| 内容 | 人工抽 10 条手记 | 没有凑数感；能说清是凭哪条入选条件进来的 |
| 截图 | 用脚本重拍 19 张 | 同一个版本、同一组宽度，替换旧图 |

## 7. 风险和要先定的事

风险：

- 选片和写手记的内容量最大。三榜 300 条手记，按每条 10–15 分钟算，要 50–75 小时。先做悬疑一榜，代码这边同时推进 W1 和 W2。
- 首期如果直接用真实剧照或第三方台词，版权要逐条登记。默认只保留海报和描边字。
- TMDb 的中文片名和冷门片覆盖不一定够。20 部抽样缺得多就人工补，补不到就标缺，不猜。
- 中文字体只保留用到的字之后，如果还是太大，按字符集分片，优先保证标题和数字。
- 100 行页面节点数如果压不下来，要先量再选方案：只渲染屏幕上看得到的行（虚拟滚动）、精简每行的标记，或者提高上限。
- 这台机器缺 Python 和 Node。W0 先装 Python 和 Pillow；Node 只在测试脚本需要时装。
- 范围容易膨胀。奖项和其他榜单口径已经写进“不做”，新需求另写方案。

开工前要先定：

1. 选片办法用权威榜、自己算，还是两者混合？
2. 详情页的“榜单第 N 位”怎么知道来自哪个榜单：网址带榜单编号，还是详情页列出所属榜单？
3. 首期是否去掉剧照和台词？
4. 100 行列表的节点上限维持 1200，还是按虚拟滚动后的新值？
5. 中文字体先做常用字全集，还是只保留页面实际用到的字？
